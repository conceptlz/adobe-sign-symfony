    Testing your application

    Your tests should never email real signers or depend on Adobe being up. This page shows how to replace the HTTP client the SDK uses in the test environment, script Adobe's responses, assert on what your code sent, and drive the webhook and OAuth routes from WebTestCase. The patterns are the ones the bundle's own test suite uses.

    Where to fake: the PSR-18 client

    You could mock AdobeSign or AdobeSignManager, but you would then be testing your mocks: the builders, the JSON they produce, the data-centre lookup and the error mapping would never run. Fake one level lower instead. Every request the SDK makes goes through a single PSR-18 client, and the bundle lets you choose that client with adobe_sign.http_client. Point it at a mock in the test environment and everything above it, including the bundle's controllers, runs for real.

    Setting up the mock client

    composer require --dev php-http/mock-client

    Three details make this work:

    • The mock is public. A private service referenced only by the manager would be inlined into it, and you couldn't fetch it to queue responses. public: true keeps it addressable as static::getContainer()->get('test.adobe_sign_http').
    • The cache is a plain ArrayAdapter service. With the default cache.app (filesystem), the data-centre lookup from one test is still cached in the next, so the number of requests changes between runs. Array pools declared under framework.cache.pools are cleared after every request, which would break duplicate detection across two webhook requests in one test. A plain service is fresh per kernel and stable within it, which is exactly what tests need.
    • Retries are off. The SDK retries 429 and 503 with real waits. With max: 0 a queued error surfaces immediately as an exception.

    Know the request order

    The mock answers requests in the order you queued them, so you need to know what the SDK sends. For an Integration Key client in a fresh kernel:

    1. GET https://api.adobesign.com/api/rest/v6/baseUris: the data-centre lookup, once per kernel (then cached in test.adobe_sign_cache).
    2. Your calls, in order, against https://api.na4.adobesign.com/api/rest/v6/… (the host from the fixture).

    A forUser() client whose stored token has an api_access_point skips the lookup. A token that is about to expire triggers a refresh (POST /oauth/v2/token) before the call; store tokens that expire in the future in tests. signatureEvidence() and signatureShortfalls() send three calls: the agreement, its members, its events.

    If you queue too few responses, Http\Mock\Client quietly answers the extra request with an empty 200, which then fails somewhere less obvious. Make unexpected calls fail loudly in setUp(): self::adobe()->setDefaultException(new \LogicException('Unexpected request to Acrobat Sign.')).

    Testing a controller that sends an agreement

    staffUser() and csrfToken() stand for your own helpers. Asserting on the JSON body is the most valuable part: it proves the builder produced what Adobe expects, not just that your code called a method. The HTTPS server parameter matters because the webhook URL is generated from the test request, and the core's WebhookInfo rejects http:// URLs before sending anything.

    Simulating Adobe errors

    use Conceptlz\AdobeSign\Exception\{AccountCapabilityException, AuthenticationException, RateLimitException};

self::queue(401, '{"code":"INVALID_ACCESS_TOKEN","message":"Access token provided is invalid or has expired."}');
// -> AuthenticationException

self::queue(400, '{"code":"HYBRID_ROUTING_NOT_ALLOWED","message":"Hybrid routing is not allowed."}');
// -> AccountCapabilityException

self::queue(429, '{"code":"THROTTLING_TOO_MANY_REQUESTS","message":"Slow down."}', ['Retry-After' => '120']);
// -> RateLimitException with $retryAfter === 120

self::adobe()->addException(new \Http\Client\Exception\NetworkException('Connection refused', new \Nyholm\Psr7\Request('GET', '/')));
// -> TransportException

    Then assert on what your app does with them: the status code your exception listener chose, the flash message, the message re-dispatched with a DelayStamp. The core's errors page lists which codes map to which class.

    Asserting on the Messenger transport

    use Conceptlz\AdobeSign\Symfony\Message\AdobeSignWebhookMessage;
use Symfony\Component\Messenger\Transport\InMemory\InMemoryTransport;

self::post($client, $payload);

/** @var InMemoryTransport $transport */
$transport = static::getContainer()->get('messenger.transport.async');
self::assertCount(1, $transport->getSent());
$message = $transport->getSent()[0]->getMessage();
self::assertInstanceOf(AdobeSignWebhookMessage::class, $message);
self::assertSame('CBJCHBCAABAAnotif1', $message->notificationId());

    Assert straight after the request: the in-memory transport is a resettable service and starts empty again after the next request. To check that a duplicate produced no second message, assert getSent() is empty after posting the same payload again.

    Code that uses forUser()

    Skip the flow and put a token in the store directly:

    use Conceptlz\AdobeSign\Auth\AccessToken;

$manager = static::getContainer()->get(AdobeSignManager::class);
$manager->tokens()->put('jane@example.com', new AccessToken(
    'user-token', 'refresh', new \DateTimeImmutable('+1 hour'), 'https://api.na4.adobesign.com/',
));

self::queue(200, 'user_me');                       // no /baseUris: the token carries the access point
$manager->forUser('jane@example.com')->users()->me();

self::assertSame('Bearer user-token', self::sent(0)->getHeaderLine('Authorization'));

    With the default token_store: cache and cache.app, the store in tests is whatever cache.app is in your test environment. To isolate tests, point oauth.token_cache_pool at test.adobe_sign_cache too, or use token_store: doctrine with your test database.

    Changing configuration inside a test

    Configuration is compiled, so a test can't change signature_level at runtime. Options: a separate environment (static::createClient(['environment' => 'test_qes']) with its own config files), or a custom test kernel that takes configuration as a constructor argument, which is what the bundle's own tests/App/TestKernel.php does. For one-off checks of the manager, constructing it directly isn't supported: its constructor is internal.

    Common questions

    Can I use Guzzle's MockHandler instead of php-http/mock-client?

    Yes. Register a GuzzleHttp\Client built with a HandlerStack around a MockHandler as the http_client service, and add a Middleware::history() to inspect requests. php-http/mock-client is simpler because it records requests itself.

    Can I use Symfony's MockHttpClient?

    Yes, wrapped as PSR-18: new Psr18Client(new MockHttpClient([...])) registered as the http_client service. Its MockResponse objects work, but you inspect requests through the response callback rather than a request list.

    Should I ever test against the real Acrobat Sign API?

    Occasionally, in a separate opt-in suite with a developer account and addresses you control, because real calls send real emails. Cancel every agreement you create. Run it before releases, not on every push.

    My queued responses disappear between two requests. Why?

    The test client reboots the kernel between requests, creating a new container and a new mock. Call $client->disableReboot() right after createClient().

    Creating a webhook in a test throws "only delivers webhooks to HTTPS URLs". Why?

    The URL was generated from the test request, which is http://localhost. Set $client->setServerParameter('HTTPS', 'on'), or configure framework.router.default_uri: 'https://localhost' for the test environment.
